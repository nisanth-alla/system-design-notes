# Retries and Idempotency

## What it is

A retry is what a client does when a request might have failed — it sends the request again, hoping this time it succeeds. Idempotency is the property that makes retries safe: an idempotent operation produces the same result no matter how many times it's applied, so retrying it is never dangerous.

These two concepts are almost always discussed together because retries without idempotency are how you get double charges, duplicate orders, and duplicate emails. Retries are the mechanism; idempotency is what makes the mechanism safe to use.

## When to use it

You need retries almost everywhere network calls happen — networks are unreliable, and "did that request actually fail, or did just the response get lost?" is a question you genuinely cannot always answer from the client side. That ambiguity is the whole problem: a timeout doesn't tell you whether the server processed the request and the response got lost, or whether it never got there at all.

You need idempotency specifically whenever:

- An operation has a side effect that's bad to repeat (charging a card, sending an email, incrementing a counter, creating a resource).
- The operation sits behind an at-least-once delivery system (see [queues.md](queues.md)) — which means duplicates are not a hypothetical, they are guaranteed to happen eventually.
- Clients might retry on their own (timeouts, mobile clients with flaky connections, retry logic in an SDK you don't control).

You can skip explicit idempotency handling for operations that are naturally idempotent already — `SET x = 5` is idempotent by construction; `x = x + 5` is not.

## How to make an operation idempotent

The standard pattern is an **idempotency key**: the client generates a unique key per logical operation (a UUID, typically) and sends it with the request. The server records which keys it has already processed and what the result was. If the same key comes in again, the server returns the stored result instead of redoing the work.

```
handle_request(key, payload):
  existing = db.get(idempotency_key=key)
  if existing:
    return existing.response   # already handled, return the same result
  result = do_the_actual_work(payload)
  db.save(idempotency_key=key, response=result)
  return result
```

The key has to be generated by the client, not the server — if the server generates it, a retry after a lost response just gets a new key and does the work twice, which defeats the entire point.

Other tools in the same family:
- **Natural keys** — if the payload already has a uniquely identifying field (e.g., "invoice #4471"), you can dedupe on that instead of a separate key.
- **Conditional writes** — `INSERT ... ON CONFLICT DO NOTHING`, or a unique constraint that rejects the duplicate at the database level as a backstop even if the application logic has a bug.
- **Version checks / optimistic locking** — "update this row only if its version is still 3" prevents a stale retry from clobbering a newer write.

## Failure modes

**Retrying non-idempotent operations blindly.** The classic bug: a payment API call times out, the client retries, and both requests actually landed on the server — customer gets charged twice. The client had no way to know the first request succeeded; the fix has to be on the server side (idempotency key), not by the client trying to be cleverer about when to retry.

**Retry storms.** Every client retries immediately on failure, all at the same moment, which turns a brief blip into a self-inflicted DDoS on your own service right as it's recovering. Fix with exponential backoff plus jitter — never retry on a fixed interval at scale.

**Idempotency keys with no expiry.** If you store every idempotency key forever, that table grows without bound. Give keys a reasonable TTL — long enough to cover realistic retry windows (minutes to low hours), not forever.

**Idempotency key reused across genuinely different requests.** If a client accidentally reuses a key for two different logical operations, the server will silently return the first result for the second request. This is a client-side bug, but it's worth validating that the payload matches on key reuse, if you can, and rejecting mismatches loudly instead of silently returning the wrong answer.

**Confusing idempotent with safe.** A `GET` is idempotent and safe (no side effects at all). A `PUT` that overwrites a resource is idempotent but not safe (it does have a side effect, it's just the same side effect every time). Know which one you're building — it changes what you're allowed to retry casually versus what needs the full key-based treatment.

## Real example

A "place order" API is the canonical case. The mobile app calls the endpoint, the request succeeds server-side, but the response is lost on a flaky connection. The app, seeing what looks like a failed request, retries automatically. Without an idempotency key, this creates two orders and charges the customer twice. With one — generated client-side when the user taps "buy," sent on every retry attempt for that same purchase — the server recognizes the second request as a duplicate of the first and returns the original order confirmation instead of creating a new one.

See [`experiments/idempotency`](../experiments/idempotency) for a runnable reproduction of the double-charge bug and the fix, or watch it happen in the [live visualization](https://nisanth-alla.github.io/system-design-notes/).

## 5-line summary

- Retries exist because you often can't tell whether a failed request actually succeeded on the other end.
- Idempotency is what makes retrying safe — same input, same result, no matter how many times it runs.
- The standard mechanism is a client-generated idempotency key that the server uses to dedupe and replay the original result.
- Combine with exponential backoff and jitter so retries don't turn a blip into a self-inflicted overload.
- Any operation behind an at-least-once queue or unreliable network needs this — duplicates aren't an edge case, they're guaranteed eventually.
